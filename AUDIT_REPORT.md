## 1. 🏗️ Architecture & Code Organization

### Overall assessment: **Strong, well-structured monorepo**

The project is a clean two-tier monorepo: a Python FastAPI backend (`backend/`) and a Vite + React + TypeScript frontend (`frontend/`), glued together by Windows-first launchers (`start.bat`, `start.ps1`). The separation of concerns is clear and the conventions are documented in unusual depth (three agent-guide files: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, plus per-layer `backend/AGENTS.md` and `frontend/AGENTS.md`).

### Strengths

- **Clean router-per-resource pattern** (`backend/routers/*.py`), each owning its `APIRouter(prefix="/api/<resource>", tags=[...])` and registered centrally in `main.py` (lines 44–51). Adding a resource is a two-file change — very scalable.
- **SQLModel base-class pattern** is consistently and correctly applied in `models.py` (e.g. `ModelBase` → `Model(table=True)` → `ModelCreate`/`ModelUpdate`). The dangerous `class FooCreate(Foo, table=True)` anti-pattern documented in `AGENTS.md` §6 is avoided everywhere.
- **Typed configuration layer** (`backend/config.py`) using `pydantic-settings` with `COMPANION_` env prefix, computed properties for `cors_origin` / `resolved_db_path` / `sqlite_url`. Good separation of config from logic.
- **Alembic migrations are wired correctly**: `env.py` targets `SQLModel.metadata`, uses the shared `backend.db.engine`, enables `render_as_batch=True` for SQLite ALTER support, and `init_db()` (`db.py` lines 35–54) auto-adopts pre-Alembic databases by stamping the baseline revision then upgrading.
- **Frontend uses a centralized data layer**: `lib/api.ts` (fetch wrapper) + `lib/queries.ts` (TanStack React Query hooks: `useModels`, `useLogs`, `useCreateLog`, `useRecommend`, `useCompare`, etc.). Components never call `fetch()` directly — the convention is enforced by design and followed everywhere.
- **Lazy-loaded routes** (`App.tsx` lines 9–17) with `React.lazy` + `Suspense` + an `ErrorBoundary` wrapper — good for initial bundle size (the `Analytics` chunk with recharts is split out, 385 kB / 102 kB gzipped, loaded only when visited).
- **Consistent UI primitive layer** (`components/ui/`) — hand-written shadcn-style components using `forwardRef` + `cn()` + `class-variance-authority`. Pattern is uniform across all 8 primitives.
- **CI pipeline** (`.github/workflows/ci.yml`) runs both stacks on every push/PR: frontend (lint → test → build) and backend (ruff → compileall → pytest). This is a genuinely useful gate.

## 2. 🧹 Code Quality, Readability & Maintenance

### Overall assessment: **Clean, consistent, well-typed — minor duplication and a few latent bugs**

### Strengths

- **Strict TypeScript** is enforced (`tsconfig.json` `strict: true`, `noUnusedLocals: true`, `noUnusedParameters: true`, `noFallthroughCasesInSwitch: true`) and the production build (`tsc -b && vite build`) passes with zero errors. No `any` types found in source.
- **Typed Python throughout**: all router functions have typed params and return SQLModel instances; `config.py` uses `pydantic-settings`; enums (`ModelKind`, `Outcome`) are used for constrained string fields.
- **Centralized validation**: `SettingsUpdate` in `routers/settings.py` uses Pydantic `field_validator`s for `reminder_time` (HH:MM, 00–23/00–59) and `theme` (dark|light), with `extra="forbid"` to reject unknown keys. Quality score uses `Field(ge=1, le=10)` in both `LogEntryBase` and `LogEntryUpdate`.
- **Consistent error handling**: routers raise `HTTPException(404, ...)` / `HTTPException(400, ...)` with human-readable detail; the frontend `api.ts` extracts `body.detail` and throws.
- **Lint configs exist and pass**: `backend/ruff.toml` (ignores `E711`/`E712` for SQLAlchemy `==` comparisons — correctly justified), `frontend/eslint.config.js` (flat config with `typescript-eslint` recommended + react-hooks). Both pass clean (2 react-refresh warnings only).
- **Good use of caching in aggregations**: `routers/logs.py` `_resolve_names` (lines 71–105) caches model/category name lookups per export batch; `stats.py` and `compare.py` batch-load referenced models/categories via `.in_()` instead of N+1 queries.

### Issues found

1. **`LogForm.tsx` cannot unset `model_id`/`category_id` during edit.** Lines 111–112:
   ```ts
   if (payload.model_id === null) delete payload.model_id;
   if (payload.category_id === null) delete payload.category_id;
   ```
   Because PATCH uses `exclude_unset` on the backend (`routers/logs.py` line 166), a deleted field is simply not sent — so once a log entry has a `model_id`, the UI provides no way to clear it back to `null`. The same applies to `category_id`. This is a real functional limitation for the edit flow.

2. **`LogForm.tsx` deletes `quality_score` when falsy (line 113):** `if (!payload.quality_score) delete payload.quality_score;`. Since the valid range is 1–10, a `0` is never legitimate, so this is harmless — but the logic is fragile (it conflates "0" with "unset"). `outcome` (line 114) has the same shape and is fine since `""` is never a valid enum value.

3. **`api.ts` shallow header merge.** `request()` (lines 2–5) sets `headers: { "Content-Type": "application/json" }` then spreads `...options`. If any future caller passes `headers: { Authorization: "..." }`, it would **replace** (not merge) the `Content-Type` header. Not a bug today (no custom headers are used), but a latent footgun.

4. **Inconsistent union-type syntax.** `routers/logs.py` line 73 uses PEP 604 `tuple[str, str | None]` inside a function body, while the rest of the backend consistently uses `Optional[str]` from `typing`. Cosmetic, but breaks the "no comments / consistent style" convention.

5. **`seed.py` always force-overwrites `seed_version`.** Lines 63–68 unconditionally set `seed_version.value = SEED_VERSION` and re-add the row. This is fine while `SEED_VERSION` is a constant `"2"`, but if a future seed migration introduces versioned logic, this would clobber any per-version bookkeeping. The upsert helpers for models/categories/settings are correctly "add if missing" — only `seed_version` is "always overwrite."

6. **`main.py` SPA catch-all swallows unknown `/api/*` routes.** Lines 64–67 register `@app.get("/{full_path:path}")` returning `index.html` when `frontend/dist/` exists. Because this catch-all has lower priority than explicit routes, real API routes still work — but a typo'd API path (e.g. `/api/loogs`) returns the HTML SPA shell with a 200 instead of a JSON 404. Standard SPA trade-off, but worth a note for API consumers.

7. **`pytest.ini` globally silences `DeprecationWarning`.** Line 7: `ignore::DeprecationWarning`. This currently hides a `StarletteDeprecationWarning` advising installation of `httpx2`. Silencing all deprecation warnings is broad; a targeted filter would be safer.

8. **No Prettier / formatter for the frontend.** The backend has Ruff (lint + format-capable); the frontend has ESLint but no `prettier` or `prettier` plugin. Formatting consistency relies on individual discipline. A `.prettierrc` + `eslint-config-prettier` would close the gap (the task explicitly asked to check for `.prettierrc` — it does not exist).

9. **No Python lockfile.** `requirements.txt` uses open-ended `>=` pins with no upper bound and no `pip-compile`/`uv.lock` equivalent. The frontend correctly has `package-lock.json` and CI uses `npm ci`. A reproducible backend install (e.g. `pip-compile` output or `uv.lock`) would match the frontend's discipline and prevent surprise breakages on major upstream releases.

10. **Minor: `models.py` redeclares `name` on the table subclasses** (lines 33, 59) to add `index=True`, duplicating the `max_length=100` already on the `*Base` class. Intentional for the index, but the duplication is a small maintenance smell.

## 4. 🔒 Security, Configuration & Technical Debt

### Secret handling — **Good**

- `.gitignore` excludes `.env`, `.env.local`, `backend/database.db*`, `backend/.venv/`, `frontend/node_modules/`, `frontend/dist/`.
- `git ls-files` confirms **no secret files are tracked** — only `.env.example` (which contains only non-sensitive port/path/timezone placeholders).
- A content search for `password|secret|api_key|token=|Bearer` across `backend/**/*.py` returned **zero hits**.
- The only `https://` references in frontend `src/` are **placeholder strings** in `Settings.tsx` (lines 45, 55) for webhook URL input hints (`https://api.telegram.org/bot<token>/...` — the `<token>` is a literal placeholder, not a real token).
- Webhook URLs (Telegram/Discord) are stored in the `settings` table and never logged.
- `notify.py` `send_os_toast` passes title/body via **environment variables** (`COMPANION_NOTIF_TITLE`/`COMPANION_NOTIF_BODY`), not via string interpolation into the PowerShell script — so there is **no command-injection vector** through notification content. ✓

### Authentication & authorization — **None (by design, with caveats)**

- The API has **no auth whatsoever**. `AGENTS.md` §10 lists "Optional auth" as Phase 4. For a localhost-only tool this is acceptable, but:
  - The backend listens on `0.0.0.0:8765` by default (uvicorn default), not `127.0.0.1`. Any host on the LAN can read/write all log data and settings.
  - Because settings (including webhook URLs) are writable without auth, an attacker who can reach port 8765 could redirect notification webhooks to an arbitrary URL (a mild SSRF vector via `notify.py` `httpx.post`).
- CORS is correctly locked to `http://localhost:{frontend_port}` (`main.py` lines 36–42, `config.py` `cors_origin`), which mitigates browser-based cross-origin attacks — but does not stop direct HTTP access to the backend port.
- **Recommendation:** bind uvicorn to `127.0.0.1` in the launchers (add `--host 127.0.0.1`) until auth exists.

This is **not used** (`env.py` uses `backend.db.engine` directly), so it's harmless — but it's misleading and should be neutralized (e.g. left blank or commented with a note that `env.py` overrides it).

### Technical debt

- **Documentation drift** is the largest debt item: three of the five agent guides (`AGENTS.md` §3/§8/§12, `CLAUDE.md`, `GEMINI.md`) describe a pre-Phase-2/3/4 state of the project. An AI agent following them would make incorrect assumptions (e.g., "no tests," "dark mode only," wrong paths, missing endpoints).

- **`seed.py` `DEFAULT_MODELS`** lists "Claude 3.5 Sonnet," "GPT-4o," "Gemini 1.5 Pro" — these are already dated model names. Not a bug, but the seed will need periodic refresh to stay useful.

## 5. 🚀 Prioritized Actionable Improvement Plan

- **Fix `LogForm.tsx` cannot-clear-FK bug.** Replace the `delete payload.model_id` / `delete payload.category_id` lines (111–112) with logic that explicitly sends `null` when the user cleared the field, so PATCH can unset the FK. The backend `LogEntryUpdate` already allows `None` for these fields. *File: `frontend/src/components/LogForm.tsx`.*
- **Reconcile the agent guides with the actual codebase.** Update `AGENTS.md` §3 (structure), §8 (API table), §12 (testing — remove "No test framework is set up yet"); fix the `CLAUDE.md`/`GEMINI.md` "dark mode only" lines to reflect the real dual-theme support; correct the `C:\Users\danyo\Desktop\Uni\...` paths to the real `Daniil Perkin\1_Uni\Projekte\...` location (or, better, make the docs path-agnostic). *Files: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `backend/migrations/README`.*
- **Add numeric sanity constraints.** In `models.py`, add `ge=0` to `input_tokens`, `output_tokens`, `latency_ms` and `ge=0` to `cost_usd` (lines 82–85) for both `LogEntryBase` and `LogEntryUpdate`. Add a test for negative-value rejection. *File: `backend/models.py`, `backend/tests/test_logs.py`.*
- **Consolidate notification fetching.** In `NotificationOverlay.tsx`, remove the manual `setInterval(poll, ...)` + direct `api.get("/notifications")` (lines 16–50) and drive everything through `usePendingNotifications()` with `refetchInterval: 60_000` in `queries.ts` (currently `refetchInterval: false`).
